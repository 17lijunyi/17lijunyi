# 证据标准与启动门槛

## 1. 证据优先级

从强到弱使用：

1. 真实运行结果：页面状态变化、生成资产、错误、日志、网络/任务结果。
2. 产品源代码和配置：实际被入口引用的实现优于孤立定义。
3. 完整截图或录屏：包含时间顺序、操作前后状态和上下文。
4. 用户提供的原始输入、导出文件和项目数据。
5. 页面公开的 Agent 计划、思考摘要或结果说明。
6. 宣传材料、帮助文档和行业常识。

第 5 类只能证明产品向用户展示了什么；不能单独证明工具调用或结果成功。第 6 类只能作为待验证假设，除非用户明确要求分析宣传定位。

## 2. 一手证据门控

开始完整拆解前，必须满足：

- 至少一种一手证据：真实页面、完整截图/录屏或原始代码；
- 证据覆盖用户指定目标的关键起点和终点；
- 能识别至少一个输入、一个系统反馈和一个结果/状态；
- 已知操作权限和禁止动作。

只满足部分条件时，只做“局部拆解”，在标题和范围中明确限定。完全不满足时停在补证清单。

## 3. 完整性矩阵

| 证据维度 | 最低检查内容 |
|---|---|
| 起点 | 用户原始输入、进入方式、初始状态 |
| 过程 | 页面反馈、表单、按钮、阶段变化、异步状态 |
| 决策 | 满意/修改、方案选择、继续/中断、权限或费用确认 |
| 结果 | 真实资产、预览、导出、代码运行产物 |
| 异常 | 失败、依赖缺失、余额不足、超时、用户中断、重试 |
| 历史 | 版本、资产历史、任务记录、可回退性 |
| 一致性 | 聊天、画布、任务、资产库、接口或日志是否一致 |

“未出现”不等于“产品没有”。写成【尚未确认：当前证据未出现】。

## 4. 证据编号

建立稳定编号：`S01`截图/录屏、`P01`页面原文、`C01`代码路径、`R01`运行结果、`U01`用户原始输入。

每条证据记录来源、时间/顺序、可见原文或对象、支持的结论和限制。不要只写文件名而不说明看到了什么。

## 5. 证据等级

- **【页面/代码事实】**：证据可直接看到或从实际执行路径确认。
- **【合理推断】**：至少两项事实共同支持，但实现未直接暴露。
- **【尚未确认】**：证据不足、相互冲突或只见口头计划。

对“完成”“成功”“符合要求”使用更高门槛：必须检查真实结果或资产状态。质量结论还要查看或播放输出，不能只看成功状态。

## 6. 冲突处理

同时保留冲突来源，例如：聊天说已完成但任务仍在生成；画布有资产但资产库为空；代码定义了工具但没有调用路径；接口返回成功但页面结果缺失。

报告应说明冲突可能影响什么，不替产品决定真相源。把“哪个状态是权威”列为后续验证问题。

## 7. 补证请求

证据不足时只输出当前能确认的范围、缺失的一手证据、最优补证顺序、用户需要执行的最少动作，以及明确不会执行的敏感或破坏性动作。

优先请求完整流程截图/录屏、可访问 URL 或相关源码目录，而不是让用户用文字复述产品机制。
